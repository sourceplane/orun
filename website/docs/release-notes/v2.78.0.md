## A whole plan runs on the lane scheduler

`orun run` with `--concurrency` above 1 (or a plan whose `execution.concurrency`
is) used to schedule in batches: it launched every job that was ready, waited
for *all* of them to finish, then looked again. A job that became ready when
one job of the batch finished waited for the whole batch. A chain of four
short jobs beside one long job took the long job's time plus the chain's,
instead of the long job's alone.

The same run now uses the scheduler a [lane](../concepts/lanes.md) uses:
every job starts as soon as its own upstreams finish, at most `concurrency`
at a time, and a free slot goes to the ready job with the longest chain of
dependents behind it. The sequential path (`--concurrency 1`), `--job` and
`--lane` are unchanged. A `--job` whose upstreams are not completed is now
refused at any concurrency, as it already was at 1.

## `--component-concurrency` defaults to no cap

The flag capped how many components could have jobs in flight at once, and
defaulted to 1 so a terminal run's output stayed grouped by component. With
the batch loop, that default admitted one new component per batch: four
independent jobs of four components at `--concurrency 4` ran one after the
other, four times slower than asked. It now defaults to 0, no cap. Set it
explicitly to keep the grouping; a job of a new component then waits, holding
no slot, until a component drains.

Measured on the regression tests that pin this: four independent 300 ms jobs
at `--concurrency 4` went from 1.2 s to 0.3 s, and a 1 s job beside a chain of
four 100 ms jobs from 1.3 s to 1.0 s.

## A lane says what it waits on

Every lane in `plan.json` and every `lane-matrix` entry now carries its
`level` in the lane graph (0 when no other lane feeds it, else one more than
the deepest lane it waits on), the `upstreamLanes` it waits on and, on the
plan, the `upstreamJobs` in them. `orun plan --view lanes` shows them.

A GitHub matrix fans every lane out at once, so on a pool with room for all
of them a lane whose upstream lane is still running takes a runner and
spends it polling; with promotion, the production lanes idle for the whole
staging phase. `orun plan --github-output` therefore also writes
`lane-matrix-<k>` for each level `k`, `lane-matrix-levels` and
`lane-level-count`, so a workflow can run the levels as chained matrix jobs
and never provision a runner before the lanes it waits on are done. A pool
that reads `upstreamLanes` from the matrix can release each runner on
exactly its own upstreams. The recipe is in
[Lanes](../concepts/lanes.md#level-by-level). A plan without
`execution.lanes` is unchanged; a lane-less `lane-matrix` entry carries the
job's own depth and dependencies.

## `concurrency: auto` and `--max-lanes`

`execution.lanes.concurrency: auto` (on the lanes or on a group) sizes a
lane to the machine that runs it: `orun run --lane` reads the runner's core
count and runs that many jobs at once, so a pool that mixes runner sizes gets
the right number on each and no intent needs a constant tuned to one
instance type. The plan carries `concurrency: 0` for such a lane;
`--concurrency` still overrides it, and a plain count still works as before.

`orun plan --max-lanes N` (or `ORUN_MAX_LANES=N`) overrides the intent's
`maxLanes` for one plan, so a CI plan job can set auto mode's lane budget
from the runner pool's free capacity instead of from a constant in
`intent.yaml`. The plan records the budget and where it came from in
`metadata.lanes` (`mode`, `maxLanes`, `maxLanesFrom`: `intent`, `default`,
`flag` or `env`), and the plan summary's `lanes` line names an override.
A plan without `execution.lanes` is unchanged.
