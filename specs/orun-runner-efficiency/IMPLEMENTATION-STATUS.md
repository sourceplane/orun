# orun-runner-efficiency — implementation status

| Milestone | Status | What shipped |
|---|---|---|
| **RE0** | ✅ #741 | The analysis, the fleet model (`model.py`) and the expected effect; the scheduler probes committed as regression tests with RE1 |
| **RE1** | 🟡 in review | A whole plan at concurrency > 1 runs on the lane scheduler (`runScheduled`, one scheduler for `--lane` and the plan): each job starts when its upstreams finish; `--component-concurrency` defaults to 0 and is a gate in front of the slot gate when set; `--job` with incomplete upstreams is refused at any concurrency; regression tests in `internal/runner/schedule_test.go` |
| **RE2** | 🟡 in review | `plan.lanes[]` carries `level` (depth in the lane graph, not the jobs' lowest level: what a levelled workflow needs), `upstreamLanes` and `upstreamJobs`; `lane-matrix` entries carry `level` and `upstreamLanes` (a lane-less plan: the job's depth and dependencies); `--github-output` adds `lane-matrix-<k>` per level, `lane-matrix-levels` and `lane-level-count`; `--view lanes` shows level and upstreams; the level-by-level recipe in `concepts/lanes.md`. `estimatedSeconds` and `vcpu` wait for their sources (RE5, RE3) |
| **RE3** | 🟡 in review | `execution.lanes.concurrency: auto` (lanes and groups; `model.LaneConcurrency`): the plan carries 0 and `orun run --lane` resolves it to `runtime.NumCPU()` on the runner, `--concurrency` overriding; `orun plan --max-lanes` / `ORUN_MAX_LANES` override the intent's budget for one plan, recorded in `plan.metadata.lanes` (`mode`, `maxLanes`, `maxLanesFrom`) and named on the summary line. Deliberately opt-in rather than the default: the default stays 4 until RE5's declared `cpu` tells auto what a job needs (the lanes docs measured concurrency 4 on 2 vCPUs at 1.8× slower per job, and deploy jobs are mostly network-bound) |
| **RE4** | 🟡 in review | `.git` is never staged; a staged job's env gets `GIT_DIR`/`GIT_WORK_TREE` (the source repository) and `TURBO_CACHE_DIR` (one cache per run); `--isolation component` copies only `job.path` and links every other top-level entry; composition steps with `scope: lane` (run steps, leading) run once per process for every job whose step is identical after templating — the first job runs it in the shared tree, the rest wait and reuse it (`shared with <job>`) — and a job's private tree is staged after them with dependencies kept (top-level `node_modules` linked, nested ones copied). Not in this milestone: sharing `use:` setup actions (their exported env is per job); `component` as the `auto` default (unsafe while compositions run their own install per job) |
| RE5 | ⏳ | Declared `resources`; weighted, critical-path packing; `--weights` |
| RE6 | ⏳ | Signal drain, resume at step, the server's lease TTL in the client |
| RE7 | ⏳ | Event-driven waits; default job and step timeouts |
