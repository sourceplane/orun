## `orun baseline new --from bst_…`

The console's baseline flow ends in a **Review** step that has already
collected everything a build needs: the baseline at its tag, the repository,
every input and the connection each provider builds against. Until now the
only thing that step could do with it was start a cloud session. It now hands
out a bootstrap id, and this release lets the CLI build from that id alone:

```bash
orun baseline new --from bst_7K2M9QAZ --workspace ws_537EHJPC \
  --local --out ./test-123 --run-hooks
```

- **Nothing typed twice.** The id fills what the flags would — the baseline
  address, `--repo` or `--repo-link`, the inputs. An explicit flag still wins
  and `--set` still adds. Inputs the build document does not declare (the
  platform derives some, such as `apibaseurl`) are left out rather than
  refused.
- **No token in the record.** Connections travel as ids; the hooks resolve
  them through the workspace exactly as a platform build does.
- **The platform knows who is building.** Before anything is fetched the
  command records which door took the bootstrap — `--by cli` (the default)
  or `--by agent` from a coding agent — and the workspace's Overview reads
  *continued from the orun CLI* or *continued in a coding agent*. First writer wins: a bootstrap
  another door already took keeps that door's word, and the command says so.
- **Refusals are the platform's, verbatim.** A bootstrap that never reached
  Review answers `409 not_resolved` naming the step or the missing provider;
  an id that is not this workspace's answers `404`.

`--from` works with `--via-platform` too, where it is the same request the
Review page's cloud-session button makes.

See [`orun baseline new`](../cli/orun-baseline.md#--from-bst_).
